# Durable SQLite Review Job Queue

**Status: accepted.** Review Jobs enter a durable SQLite queue before execution. The web process only validates and enqueues jobs. An independently started worker command claims jobs and runs a fixed worker pool with one configurable global concurrency limit; the first implementation has neither in-Web background workers, per-backend quotas, nor an external broker. Workers use the web service's OS account by default, and deployments may configure a separate worker account when stronger isolation is required.

Failures before the Agent Backend starts may receive up to three automatic retries with exponential backoff. Once the Agent has started, `failed` and `timed_out` jobs are not retried automatically because delivery may already have happened and replay could duplicate a review note or fix MR.

The web process normalizes each accepted webhook and persists only the immutable fields required to execute the Review Job; the durable queue does not retain the full webhook payload. If a worker crashes after the Agent has started, lease recovery marks the job `failed`, attempts orphan workspace cleanup, and does not requeue it. This treats an unknown partial delivery as unsafe to replay.

Transport idempotency has two layers. Enqueue-time deduplication uses provider, review URL, source revision hint, and target revision hint while ignoring webhook action aliases. After fetching, the worker checks the resolved `SOURCE_REVISION` and `TARGET_REVISION` pair so missing or stale webhook target hints cannot repeat an already reviewed snapshot. When a newer revision arrives for the same review URL, queued older revisions are superseded. A revision already running is not force-stopped; it may complete before the latest revision is reviewed. Jobs for the same review URL are serialized so their previous revision and Rolling Review Note state cannot race, while different reviews still run concurrently within the one global limit.

On SIGTERM, a worker stops claiming new jobs and waits for a configurable shutdown grace period. After that grace expires it terminates active Agent process groups, marks their jobs `failed`, and runs cleanup. Completed Job records and Agent Results are retained for 90 days by default; deployments may configure the retention period, and cleanup deletes expired records in bounded batches.
